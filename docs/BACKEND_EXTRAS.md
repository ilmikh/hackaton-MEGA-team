# Печатные формы, выезд жильцов и общий фонд

Все endpoints используют текущую cookie-сессию. Изменяющие запросы требуют
`X-CSRFToken`; сервер проверяет роль, независимо от видимости кнопок в интерфейсе.
Внешней интеграции с ЛКП, рассылки и автоматического выселения нет.

## Формы для печати

| Endpoint | Доступ | Результат |
| --- | --- | --- |
| `GET /api/requests/{id}/statement` | Заявитель или администратор | HTML заявления для любого состояния заявки |
| `GET /api/requests/{id}/act` | Заявитель или администратор | HTML акта для одобренной заявки; иначе 409 |
| `GET /api/admin/bikes/{id}/act` | Администратор | HTML акта списания для статуса `scrapped`; иначе 409 |

Заявления покрывают `register`, `place`, `move`, `release`, `donate`, `withdraw`,
`transfer`. При передаче указан получатель, при перемещении — исходное и
запрашиваемое места. Подписи и дата подписания остаются пустыми; наличие записи
в реестре не представляется как подпись человека. Все значения экранируются.
HTML можно открыть отдельной вкладкой и распечатать средствами браузера.
Чужая заявка возвращает 404, отсутствие сессии — 401, административная форма
для обычного жильца — 403.

При одобрении заявки сохраняется `requests.snapshot_json`: акт использует
зафиксированные поля, включая описание велосипеда, заявителя, получателя,
места и решение. Последующие исправления профиля/карточки не меняют этот акт.
Старые одобренные заявки без снимка явно помечены как формы по текущим данным.
Заявление формируется по текущим сведениям; исторический снимок используется
именно для акта. При переводе в `scrapped` в той же транзакции сохраняются
событие `status` с `details=scrapped` и отдельное `scrap-snapshot` с описанием
велосипеда, владельцем, датой и исполнителем. Акт списания использует этот
снимок, связанный с последним событием статуса, и показывает историю с датами
UTC из `events`. Последующее изменение карточки, профиля владельца или
администратора не переписывает сохранённые сведения. Повторное назначение
уже установленного `scrapped` ничего не меняет. Старые списания без снимка
явно используют текущие данные. Если события списания нет, дата и исполнитель
обозначаются как незафиксированные.

## Ручная дата выезда

`GET /api/admin/users` — только администратор. Возвращает массив:

```json
[{"id":"user-id","username":"resident","name":"Имя жильца","phone":"","room":"","role":"resident","departure_date":null}]
```

Поле `departure_date` — `YYYY-MM-DD` либо `null`. Хеш пароля, сессии и CSRF-токены
в список не попадают. Список включает все учётные записи, в том числе
администраторов; интерфейс может показывать их роль.

`PATCH /api/admin/users/{id}/departure` — только администратор:

```json
{"departure_date":"2028-02-29"}
```

Для очистки передаётся `{"departure_date":null}`. Ответ — `{"ok":true}`.
Поле обязательно, лишние поля запрещены. Проверяются точный формат и
существование календарной даты; неверные данные дают 422, неизвестный id — 404.
Изменение фиксируется в журнале событий.

`GET /api/me/reminders` — текущему пользователю:

```json
[{"message":"Не забудьте забрать велосипед и оформить снятие с учёта к дате выезда: 29.02.2028.","departure_date":"2028-02-29","bike_count":1}]
```

Возвращается `[]`, если дата не задана или нет своих активных велосипедов.
Активный велосипед имеет `status=registered` и `review=pending|approved`.
Ожидающая регистрация учитывается; отменённая/отклонённая — нет. Напоминание
показывается при любой заданной дате, без таймера, срока рассылки и внешних
уведомлений. Дата не добавляется в `/api/me`, карточку владельца велосипеда
или ответ QR для другого жильца. Своя дата доступна через напоминание.

## Выдача велосипеда из общего фонда

`PATCH /api/admin/bikes/{id}/owner` — только администратор:

```json
{"username":"resident"}
```

Ответ — `{"ok":true}`. Получатель должен существовать (иначе 422), велосипед
должен быть одобрен и иметь статус `registered` либо `donated` (иначе 409).
Назначение выставляет нового владельца и `status=registered`, закрывает
ожидающие заявки прежнего владельца с причиной и сохраняет событие `owner`
с `old_owner_id`/`new_owner_id`. Повторное назначение того же владельца
зарегистрированного велосипеда не создаёт лишних изменений.

`PATCH /api/admin/bikes/{id}/status` с `{"status":"donated"}` очищает
`owner_id` так же, как одобренная заявка на дарение. Прежний владелец теряет
доступ к карточке и фотографии; QR больше не показывает его контакт.
Возврат в `registered` без владельца даёт 409: сначала нужен endpoint `owner`.
Неактивный статус освобождает место и отклоняет ожидающие заявки с причиной,
исполнителем и датой. Их последующее одобрение возвращает 409.
Дополнительно при одобрении проверяются текущие `review` и `status`, чтобы
нельзя было закрепить место за уже списанным велосипедом.

Жилец не может редактировать описание неактивного велосипеда (409).
Администратор сохраняет возможность исправления с записью в журнале.

## Миграции и ограничения запросов

`init_db()` идемпотентно добавляет `users.departure_date TEXT` и
`requests.snapshot_json TEXT` в существующую БД под write-lock, не создавая
пользователей или паролей. Старые строки получают `NULL`; существующие
пользователи, пароли и заявки сохраняются. Вставки пользователей используют
явные имена колонок.

Чистый ASGI middleware ограничивает тело POST/PATCH/PUT до разбора FastAPI:
12 MiB для `POST /api/bikes` и `POST /api/qr/scan`, 256 KiB для остальных.
Проверяются и Content-Length, и фактически принятые байты, включая chunked.
Для upload endpoints сессия и CSRF проверяются до чтения тела и записи
`UploadFile`. Отсутствие сессии даёт 401, неверный CSRF — 403, превышение — 413.
Лимиты самих изображений остаются 2 MiB для карточки и 10 MiB для сканирования.
Неверный URL QR, включая повреждённый IPv6-host, возвращает 422.

Создание сессии повторно сверяет пароль под той же блокировкой записи,
что и смена пароля. Логин, проверивший уже заменённый пароль, получает 401
и не создаёт новую сессию после отзыва старых сессий.

## Проверка

`python -m unittest discover -s tests -p test_registry.py -v` использует
изолированные временные БД. Покрыты все виды заявлений, права и экранирование,
снимок акта и старые записи без снимка, миграции, даты и приватность QR,
списание с историей и неизменяемым снимком, закрытие ожидающих заявок, выдача фонда, гонка пароля,
лимиты multipart/chunked/JSON и ранний отказ до записи загруженного файла.
