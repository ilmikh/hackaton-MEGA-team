# Подключение фронтенда к FastAPI

Это фронтенд на HTML/CSS/JavaScript. Бэкенд, аутентификация, БД и реальные операции с местами здесь не реализованы. Демоданные не доказывают работу сервера.

## Файлы и запуск
- frontend/index.html — рабочий режим API: без демоданных, переключения ролей и локального хранения профилей.
- frontend/demo/index.html — автономное демонстрационное приложение с явной плашкой. localStorage используется ТОЛЬКО здесь.
- frontend/static/veloregistry/app.js — интерфейс и переходы.
- api.js — единственный слой HTTP, отдельный демоадаптер в том же файле.
- scanner.js — только превью камеры, снимок и выбор фото; распознавание делает бэк.
- QR-библиотеки удалены. Контракт серверной генерации и распознавания: [QR_BACKEND.md](QR_BACKEND.md).
- docs/design — ровно восемь актуальных макетов для обоих фронтенд-разработчиков. Это концепты, не скриншоты реализации.

Локальное демо: из корня репозитория запустить python -m http.server 8000, открыть http://localhost:8000/frontend/demo/index.html. Через file:// модули и камера не работают. Реальная камера требует HTTPS либо localhost и разрешения пользователя.

Для FastAPI:
1. Раздавать frontend/index.html по выбранному URL приложения.
2. Подключить frontend/static как /static. HTML ссылается на /static/veloregistry/….
3. Раздавать тот же index.html по /q/b/{token} и /q/p/{token}; начальный QR-переход обрабатывается после GET /api/me. Ссылка должна быть доступна телефонам в целевой сети.
4. API и фронт желательно разместить на одном origin. Конкретный механизм входа реализует бэк; текущий адаптер использует same-origin cookie-сессию. JWT в localStorage и экран входа не добавлены.
5. При необходимости ДО module-скрипта добавить window.VELO_CONFIG = {apiBase:"/api", publicOrigin:"https://campus.example", loginUrl:"/login", routes:{"/map":"/parking-map", "/requests":"/requests", "/admin/map":"/admin/parking-map", "/admin/requests":"/admin/requests"}}. Все маршруты routes проверяются на тот же origin. Не указывать секреты в этой конфигурации.

Постоянные QR-ссылки, токены и их проверку реализует бэк. Фронт отправляет ссылку на /qr/resolve и показывает готовый ответ, а не разбирает QR самостоятельно.

## Ответственность фронтендеров
Azik: мой профиль; собственные велосипеды; регистрация; отдельная страница велосипеда; изменение описания; показ/скачивание готового QR сервера; камера и загрузка фото для отправки на сервер. В административном режиме — сканирование полной карточки, чтение/редактирование описания велосипеда, профиль владельца и комната ЛКП.
Тиммейт: карты, списки свободных/занятых мест, заявки, их обработка и административная карта/списки.

Ссылки на карту и заявки есть, но их страницы не реализуются за тиммейта. Пока интеграция отсутствует, отображается «Раздел пока недоступен». Полные CRUD пользователей, смена ролей, смена владельца и жизненного статуса — отдельные административные функции вне этой поставки.

## Контракт: общие правила
JSON в UTF-8. Названия полей ниже согласовать с бэком. Адаптер ожидает ответы объектов без обёртки data, списки как массив либо {results:[…]}. Если у бэка другие поля — менять api.js, не все экраны.
Все ID — строки, даты — ISO 8601, отсутствующие значения — null. photo_url — доступный пользователю URL JPG/PNG/WebP; разрешения на оригиналы фото проверяются сервером.

Базовый профиль:
{ "id":"u1", "display_name":"Алина Крылова", "contact_type":"telegram", "contact_value":"@alina_k", "role":"resident" }
role: resident или admin. contact_type: telegram либо phone.
Имя и контакт можно редактировать в текущей версии; если имя должно приходить только из ЛКП, бэк запрещает изменение и фронт делает поле readonly.
Комната не входит в GET /me, чужой QR или обычные ответы парковок. Админ получает её только из административных ответов. Нет данных ЛКП => null. У пользователя поле комнаты отсутствует.

Базовый велосипед:
{ "id":"b1", "public_number":"В-001", "model":"Stels Navigator", "color":"Сине-белый", "special_marks":"Белые крылья", "photo_url":null, "review_state":"approved", "status_label":"Зарегистрирован", "parking_name":"Гамма — павильон", "spot_code":"Г-01" }
review_state: pending / approved / rejected. Учётный статус — отдельное поле status_label (при необходимости добавить status_code).
Для административной полной карточки добавить owner_id и owner: профиль владельца, dormitory_name, room_number, lkp_synced_at. Комнату хранить строкой, не числом.

## Endpoints этой части
| Метод | URL | Тело / результат |
|---|---|---|
| GET | /api/me | Текущий профиль и роль; 401 если входа нет |
| PATCH | /api/me | JSON display_name, contact_type, contact_value; вернуть обновлённый профиль |
| GET | /api/me/bikes | Только собственные велосипеды |
| GET | /api/me/bikes/{id} | Собственная полная карточка |
| PATCH | /api/me/bikes/{id} | JSON model, color, special_marks; вернуть обновлённую карточку |
| POST | /api/me/bikes | multipart/form-data: photo (файл), model, color (текст), special_marks (может быть пусто), target_spot_id. Вернуть созданный велосипед (201) |
| GET | /api/me/bikes/{id}/qr | {image_url:"/api/…/qr.png",download_url:"/api/…/qr.png"}; готовое изображение сервера |
| POST | /api/qr/scan и /api/qr/resolve | Фото или ссылка; ограниченный результат. См. QR_BACKEND.md |
| POST | /api/admin/qr/scan и /api/admin/qr/resolve | Фото или ссылка; полный результат, только admin |
| GET | /api/admin/bikes | Полный список; демопросмотр и будущая интеграция административных списков |
| GET/PATCH | /api/admin/bikes/{id} | Полная карточка; PATCH только разрешённые описательные поля |
| GET | /api/admin/bikes/{id}/qr | image_url / download_url готового PNG сервера |
| GET | /api/admin/users/{id} | Профиль владельца + dormitory_name, room_number, lkp_synced_at |

Владелец при POST определяется по сессии. owner_id и роль не передаются из регистрационной формы. Бэк отсекает лишние поля PATCH, чужие ID, незаконный переход статуса и изменения ожидающей регистрации.
Регистрация содержит выбранное место: сервер создаёт единую заявку register с target_spot_id, не отдельное мгновенное закрепление. При отправке и одобрении проверить доступность места, активность и владельца. Одобрение регистрации и закрепление — одна транзакция. До решения место не бронируется. При конфликте 409, поля и фотография на фронте сохраняются для повторной попытки.
Фото: допустимы JPEG/PNG/WebP до 2 МБ, особые приметы до 500 символов, модель до 120, цвет до 80; цвет не enum. Бэк проверяет реальное содержимое файла, размеры и права, а не только MIME клиента.
Неподтверждённому велосипеду QR не выдавать. После смены владельца URL остаётся прежним, карточка показывает актуальные данные.

## Ошибки и cookie-вход
Поддерживается {code,message,field_errors:{поле:"ошибка"}}.
Также поддерживаются стандартные FastAPI ошибки {detail:"описание"} и 422 с detail:[{loc:["body","поле"],msg:"ошибка",type:"…"}].
401 — вход; 403 — запрет; 404 — не найдено; 409 — конфликт; 422 — валидация; 204 — успех без тела (для updateMe всё же нужен профиль).
Для PATCH/POST адаптер читает cookie csrftoken и отправляет X-CSRFToken. FastAPI сам такую защиту не добавляет: бэк должен реализовать и согласовать cookie+header или заменить адаптер под выбранный механизм. Cookie сессии должна быть HttpOnly, а csrftoken доступна JS. CORS, SameSite и защита записи — ответственность сервера. Размещение на одном origin избавляет от отдельного CORS для этой поставки.
Не полагаться на скрытые пункты меню: любой административный endpoint проверяет роль, каждый /me endpoint — принадлежность. Полные данные не передавать жильцу с расчётом скрыть их CSS.

## Интеграция карты тиммейта
Текущий маршрут регистрации #/register. Кнопка выбора вызывает отменяемое событие velo:pick-place.
Пример подключения на странице:
window.addEventListener("velo:pick-place", event => {
  event.preventDefault();
  // Открыть свою карту / модальное окно, показывать только свободные места.
  // После выбора:
  event.detail.onSelect({id:"spot-id", code:"Г-06", parking_name:"Гамма — павильон"});
});
Callback актуален, пока форма не сменила маршрут. Для отдельной страницы карты вернуться в оболочку через:
window.VeloRegistry.selectPlace({id:"spot-id",code:"Г-06",parking_name:"Гамма — павильон"});
или событие window.dispatchEvent(new CustomEvent("velo:place-selected",{detail:{…}})).
Выбор валидируется как структура, но актуальную свободность всегда перепроверяет бэк.

Форма хранит черновик и File в памяти вкладки: при внутреннем переключении разделов они сохраняются, при перезагрузке исчезают. Для карты НЕ делать полную перезагрузку страницы, если нужно сохранить выбранное фото. Предпочтителен общий shell/модальное окно и callback. Перенос файла между отдельными документами в этом PR не реализован.
В деморежиме вместо ещё не подключённой карты — явно подписанное окно выбора двух вымышленных свободных мест. Это не реализация карты тиммейта.

## Интеграция заявок и QR парковки
Кнопка «Добавить заявку» вызывает отменяемое velo:navigate с detail:
{path:"/requests",context:{bikeId:"b1",create:true}} (либо /admin/requests).
QR парковки после ответа бэка: {path:"/map",context:{parkingId:"…"}} (либо /admin/map).
Обработчик тиммейта должен вызвать event.preventDefault() и открыть свой раздел с этим контекстом.
Если обработчика нет, контекст записывается в sessionStorage под velo-navigation и маршрут переключается. Запись заменяется при следующем переходе; читающий раздел должен удалить её после получения.
Для прямых URL используйте VELO_CONFIG.routes. При обычном переходе по меню дополнительного контекста нет.
Никакая из этих клиентских точек не заменяет проверки владельца, свободности и прав сервером.

## Проверки и ограничения
tests/frontend.cjs запускает временный HTTP-сервер и Playwright. Нужны Node и установленный playwright (npm install --no-save playwright и npx playwright install chromium) либо установленный Edge с BROWSER_CHANNEL=msedge.
Команда: node tests/frontend.cjs. PLAYWRIGHT_MODULE позволяет указать абсолютный путь к существующему пакету; тестовые зависимости не нужны для запуска самого сайта.
Актуальные проверки после удаления клиентской QR-логики: отправка фото/multipart/CSRF, серверные ошибки и повтор, разный ответ для ролей, показ и скачивание готового PNG, серверное разрешение ссылки, сохранность регистрации и остановка камеры. Бэкенд заменён mock HTTP-ответами; QR не декодируется на клиенте.
Физическая камера и реальный FastAPI/ЛКП пока не проверены. Реальный вход/HTTP-сессии, права на сервере, рассмотрение заявок, импорт комнаты и транзакции должен подключить бэк.
Для демонстрации запуска camera-track cleanup теста используется подставной MediaStream; реальное разрешение камеры остаётся проверкой на устройстве.
