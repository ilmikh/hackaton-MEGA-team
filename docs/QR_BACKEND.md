# QR: границы фронта и бэка (FastAPI)

По решению команды QR-логику выполняет бэк. Клиентские библиотеки jsQR и qrcode-generator удалены, генерации/декодирования/разбора QR-токенов во фронте нет.

## Что осталось на фронте
- Превью камеры, остановка камеры при уходе, снимок по кнопке «Сфотографировать QR».
- Выбор JPG/PNG/WebP до 10 МБ и отправка файла.
- Ожидание, сообщение об ошибке, закрываемое окно ответа, «Сканировать ещё».
- Показ готового QR-изображения сервера и скачивание готового PNG без перерисовки.
- Отправка QR-ссылки серверу, включая прямой вход по /q/b/… и /q/p/….
В демо без API распознавание, получение QR и разрешение QR-ссылок недоступны. Они не имитируются.

## Что реализует бэк
1. Генерация изображения QR, постоянной ссылки и токена. Хранение связи с велосипедом/парковкой.
2. Распознавание файла с QR, проверка содержимого, извлечение и проверка ссылки/токена.
3. Поиск объекта и проверка роли/принадлежности. Жильцу вернуть только имя и контакт; админу — полные данные.
4. Генерация/раздача PNG с проверкой доступа.
5. Проверка типа/размера/содержимого загруженного файла, отсутствие QR и понятные ошибки.
6. Не загружать произвольный URL из QR: разобрать его, проверить разрешённый origin и формат токена, найти свой объект. Отрицать внешние и неизвестные QR.
7. Не регистрировать и не менять велосипед при чтении QR.

## Предлагаемые endpoints
Все запросы same-origin, cookie-сессия; POST использует X-CSRFToken, как остальной API. Согласовать механизм с командой.
- POST /api/qr/scan — multipart/form-data, поле photo. Только ограниченные данные.
- POST /api/admin/qr/scan — тот же файл, только admin, полный результат.
- POST /api/qr/resolve — JSON {url:"https://…/q/b/…"}, сервер проверяет и разрешает ссылку.
- POST /api/admin/qr/resolve — административный вариант.
- GET /api/me/bikes/{id}/qr — JSON {image_url:"/api/…/qr.png",download_url:"/api/…/qr.png"}.
- GET /api/admin/bikes/{id}/qr — административный вариант.
image_url и download_url должны вести на текущий origin. GET изображения возвращает image/png, проверяя доступ; для скачивания frontend получает готовый blob. URL не формирует QR на фронте.

Ответ распознавания/разрешения велосипеда для жильца:
{ "kind":"bike", "bike": { "public_number":"В-001", "owner": { "display_name":"Иван", "contact_type":"telegram", "contact_value":"@ivan_s" } } }
Для админа bike — полная карточка с id, model, photo_url, status_label, spot_code и owner с room_number.
Для парковки:
{ "kind":"parking", "parking_id":"p1" }
Фронт передаёт parkingId в раздел карты тиммейта, не извлекает его из QR самостоятельно.

Ошибки: 401/403 — доступ, 404 — неизвестный код, 422 — файл/QR не читается, 413 — превышение лимита. Поддерживаются стандартный FastAPI detail и формат message/field_errors.
Камера делает один снимок по нажатию; автоматическая непрерывная отправка кадров не включена. Реальный FastAPI и физическую камеру нужно проверять с командой.

## Проверка
tests/frontend.cjs проверяет HTTP-границу на mock-ответах: фото/multipart/CSRF, ошибка и повтор, ограниченный/полный ответ, показ и скачивание PNG сервера, разрешение прямой ссылки бэком, сохранность регистрации и остановку камеры. Это не проверка распознавания бэка.
